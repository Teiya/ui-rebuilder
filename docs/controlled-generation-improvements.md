# 受控生成与资产溯源改进计划

记录日期：2026-10-12  
状态：待实施建议，未排期；本次仅补充文档，未运行生成实验或修改实现。

本计划补充 [M2 至 M5 迁移路线](migration.md)，优先统一资产来源记录，再逐步接入可恢复的生成与修复适配器。保留 UIIR、确定性资产处理、OpenPencil 五页设计源和人工验收主链路；ComfyUI 与 ImageGen 作为候选来源并存，不预设全面替换现有方案。

## 核查基线与已有能力

本次文档核查基于 UI Rebuilder [`b7a0a55`](https://github.com/Teiya/ui-rebuilder/tree/b7a0a55bce91216b64b2ba5a5a2a9671f13bdbc0) 的远端文件。没有核查任何本地未推送改动，也没有实测下述 Comfy CLI 接入方式。后续实施应先复核消费项目锁定的实际版本，不因默认分支较旧而回退依赖或改写锁文件。

已有能力应直接复用：

- [规范化重建流程](workflow.md)：reference、style profile 和 job 进入 UIIR，再输出资产清单、预览、五页 `.fig`、结构报告和人工视觉验收材料。
- [确定性资产处理](../src/ui_rebuilder/pipeline/assets.py)：裁切、透明边界处理、等比缩放、九宫格、平铺、目标尺寸和 Alpha 检查。当前标记为 `generated` 的资产也可由任务引用已有生成图片；这一标记不表示主流水线会现场调用模型。
- [ComfyUI 模板](../workflows/comfyui/README.md)、[提交脚本](../scripts/queue_comfyui_workflow.py)以及[模型锁](../third_party/models.lock.json)：已有手动提交和模型哈希验证基础。
- [工作区隔离](architecture.md#workspace-concurrency-boundary)：已有独立任务目录、并行构建和汇总验证；失败隔离与质量检查应扩展既有机制。
- [适配器边界](architecture.md#adapter-boundaries)：通用 `RecoveryAdapter`、`GenerationAdapter` 和 `EngineRecipeExporter` 仍是后续接口方向。自动引擎导出尚待实现，不代表消费项目不能已有手工 handoff 和 Unity 交付流程。

消费项目已有的固定模型与 seed、历史状态轮询、后处理和候选评分脚本，应在接入前盘点并抽取公共部分。专用提示词、掩码、原图、基准结果和审核记录继续由消费项目保存，不复制到公开工具仓库。

## P0 统一端到端来源记录

优先解决 job、资产清单和 handoff 各自描述来源时发生的语义漂移。需要防止的情形包括：同一图片在 job 中标为 `generated`，在候选记录中属于模型生成，交付说明却写成原稿提取。导出阶段不能根据文件所在目录重新推断来源。

- [ ] 定义稳定的 provenance ID，并让 job、候选、asset manifest、UIIR 资产绑定和引擎 handoff 引用同一记录。
- [ ] 保存来源类型及处理链、workflow 版本与哈希、工具/模型标识与可获得的模型哈希、输入图和 mask 哈希、seed、完整参数、后处理版本、原始输出与最终输出哈希、审核状态及其适用范围。
- [ ] 区分外部生成图片的导入与适配器执行。无法取得模型或 seed 等历史信息时，显式记录未知与原因，不能补造值；导入、裁切或修复也不能抹掉上游生成来源。
- [ ] 验证 job → manifest → handoff 的来源类型、候选 ID、输出哈希和批准版本一致；缺失或冲突时阻止误标为已批准，并给出可追溯诊断。

字段名称和记录存储方式需在实施时做 Schema 设计。本节是所需信息清单，不代表现有 Schema 已支持这些字段。

## P1 统一生成与修复适配器

从已有脚本抽取适配器，分别承接 ImageGen、ComfyUI 生成候选和修复流程：

- [ ] 统一候选请求、执行状态、输出文件、来源记录与错误契约，允许消费项目继续导入已有图片。
- [ ] 适配器只负责素材生成或修复。文字、数值、层级、布局和交互状态继续由 UIIR 及消费项目契约管理。
- [ ] 输出先进入候选区，再接入已有确定性后处理、manifest、预览和 `.fig` 构建；保留原稿提取、现有批准素材与新生成候选供比较。
- [ ] 用相同素材目标和验收条件比较 ImageGen 与 ComfyUI。局部拓扑更好或自动分数更高，都不足以证明整体视觉质量更好，也不能据此全面替换既有来源。

### 同目标环境 preflight

- [ ] 在真正执行的同一 local/cloud 目标读取 live `object_info` 或等价节点 Schema，检查节点类型、参数类型/枚举、连接、模型可用性及输入/输出节点契约。
- [ ] 校验输入图与 mask 的尺寸和语义、输出图数量/格式/尺寸/Alpha 预期；将 Schema 快照与目标环境标识纳入运行记录。
- [ ] 保留现有工具与模型 hash lock，并与运行目标实际模型核对。缓存或离线 Schema 只能提供诊断；标记为 stale 或无法验证的结果不能报告为 live preflight 通过。
- [ ] 将官方模板检查作为辅助检查。其 custom-node 依赖报告不等于节点已安装、兼容或能成功执行；仍需在实际目标验证。

安装节点、下载模型、上传消费项目素材和启用云端执行属于独立操作，需有对应许可与授权；preflight 不应静默执行这些操作。

## P2 持久状态与可恢复执行

在既有提交、轮询和后处理脚本上补足持久状态，不重新搭建一套重复的批处理系统。

- [ ] 持久保存逻辑任务 ID、provider job ID 或 `prompt_id`、目标环境、阶段、输入/参数指纹、输出位置和恢复信息。
- [ ] 区分 submitted、running、completed、failed、状态未知，以及下载、后处理、待审核等阶段；具体枚举在接口设计时确定。
- [ ] 等待超时或连接中断后先查询原任务。超时不等于生成失败；不能直接重新提交并造成重复付费。
- [ ] 允许下载和确定性后处理独立重试；已经生成成功的结果不因这些阶段失败而重新生成。
- [ ] 缓存键纳入 workflow、模型、输入/mask、seed、参数和后处理版本；缓存命中仍需校验输出哈希与审核状态。
- [ ] 显式固定 local/cloud 和目标服务，避免登录状态变化造成隐式切换。缺少权限、预算或付费确认时暂停对应操作，不自动接受付费或升级。

## P2 资产级质量门与批准版本

复用现有 Alpha 检查、预览、结构门和人工审核，按资产类型补充实际使用尺寸的检查：

- 圆环：中心留白、环宽、圆心、轮廓连续性和缩放后的视觉重量；
- 卡框/面板：四边线宽、角部一致性、九宫格保护区及不同目标尺寸；
- 图标：轮廓可读性、实际尺寸辨识度和等比缩放；
- 共通项：透明区域、浅/深底边缘、色边、污染像素和输出哈希。

- [ ] 将工作流图合法、生成完成、素材验收、Unity 导入、Prefab 与消费项目运行时（如 ET）验证分别记录为独立质量门。未执行的门保持 pending，不以另一个阶段成功代替。
- [ ] 保留原有五页 `.fig` 结构检查；`complete-fig-pending-visual-approval` 仍仅表示结构完成。
- [ ] 将批准绑定到确切候选、输出哈希和审核范围。素材批准不自动代表 Unity/运行时通过；完整交付需相关质量门和人工验收均通过。
- [ ] 新候选即使评分最高也只能提交比较，不能覆盖批准版本。后处理变化、重新生成或关键导入设置变化，应使受影响的验收重新进入待核查状态。

Unity/ET 检查由消费项目执行；通用核心只定义可扩展的质量门与结果契约，不内置游戏业务或直接修改 Prefab。

## 可选的 Comfy CLI 接入

Comfy CLI 可用于节点/模型发现、workflow 校验、任务查询和结果下载，作为适配器实现选项。实施时应固定 CLI 版本并核对实际命令和返回格式。

- 官方 CLI 内置 skills 支持 AGENTS.md 感知工具，可作为 Codex 的接入参考；独立 `comfy-skills` 仓库中的 `comfy-cloud` 是 Claude Code 的 Comfy Cloud MCP 插件，两者不是同一条接入路径。
- Comfy workflow recipes 可作为可复用工作流的可选来源格式。已经稳定的 headless API graph 不强制迁移。
- Comfy 的 workflow recipe 与 UI Rebuilder 的 UI 组装 recipe 分属不同层，不能把模型工作流当作 UI 布局或引擎 assembly 的事实来源。
- 引入 CLI、recipes 或新的生成提供方均需独立验证，不因本计划被记录而修改工具锁、模型锁或消费项目依赖。

## 最小试点及验收

后续选一个消费项目仍在使用的卡框或图标作为试点。历史离线样本只用于回归参考，不为试点恢复已删除界面。公开自动化测试只使用合成或许可明确的可再分发素材。

试点实施顺序：

1. 为现有批准素材和候选建立统一来源记录，先验证 job → manifest → handoff 一致。
2. 复用已有生成/修复与评分脚本，通过同一适配器契约接入一条候选流程。
3. 验证同目标 preflight，并模拟生成等待中断、下载失败和后处理重试。
4. 在真实使用尺寸比较候选；经人工批准后固定版本，再由消费项目完成引擎与运行时验证。

试点完成的判据：

- [ ] 来源、参数和输出哈希可追踪，跨交付物语义一致。
- [ ] 中断后能确认原任务状态并恢复，不产生意外重复提交或付费。
- [ ] 原始素材、批准版本和新候选可并列比较，评分不能代替批准。
- [ ] 重建、重试和新增候选不改变已批准版本；相关质量门逐项留有结果。

本计划不承诺实施时间。完成试点后再决定是否扩大资产类型或采用 Comfy recipes。
